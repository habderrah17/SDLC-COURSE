## القسم 2: الفحص البرمجي (Coding Check)

> بيدك. بلا AI. `strict` + `noUncheckedIndexedAccess`. DB حقيقية في Docker لمهام 2.3–2.5.

### مهمة 2.1 — الهياكل الثلاثة
اكتب في ملف واحد (≤ 150 سطرًا) مع اختبارات `node:test`: (أ) `RingQueue<T>` محدودة بسياستي `reject`/`dropOldest`؛ (ب) `LRUCache<K,V>` بـ Map + قائمة مزدوجة بـ sentinels، مع `hits/misses`؛ (ج) `Heap<T>` بمقارِن مع `replaceTop`. ثم `topK(iter, k, less)` بذاكرة O(k). اختبار خاصية لكلٍّ (مثلًا: pop متكرر من الكومة = مرتّب؛ LRU بعد `get(a)` يطرد `b` لا `a`).

### مهمة 2.2 — الرسم البياني والبحث
`topoSort(deps)` بـ Kahn، مخرج حتمي، يرمي `CycleError` تسمّي الدورة. `lowerBound(n, pred)` واختبار خاصية ضد `indexOf` على 1000 مصفوفة عشوائية. ثم `bench.ts` يقيس `find`-in-loop vs Map عند 2k و20k ويطبع النسبة — أرفق المخرجات.

### مهمة 2.3 — Schema + migrations
من متطلبات نصية نعطيك إياها (مكتبة: أعضاء، كتب بعدة مؤلفين، إعارات بتاريخ إرجاع، غرامات): ERD بـ Mermaid، `0001_init.sql` بكل القيود (الأنواع الصحيحة، FK مع `ON DELETE` مبرَّر في تعليق، CHECK، فهرس فريد جزئي)، runner migrations (≤ 40 سطرًا) يعمل من عمليتين متزامنتين. اختبارات: 4 إدراجات يجب أن ترفضها DB.

### مهمة 2.4 — SQL
على schema المكتبة مع seed 100k إعارة: (أ) الأعضاء الذين لم يستعيروا قط؛ (ب) أكثر 10 كتب إعارة في شهر مع عدد المؤلفين لكل كتاب **بلا fan-out**؛ (ج) `GET /loans` بـ keyset pagination وفلتر اختياري بمعامل؛ (د) تفاصيل عضو مع إعاراته وكتبها في استعلام واحد `json_agg`. لكلٍّ: الاستعلام، النتيجة على بيانات صغيرة معروفة، و`EXPLAIN (ANALYZE, BUFFERS)` بعد الفهرس المناسب الذي تضيفه أنت.

### مهمة 2.5 — المعاملة تحت التزامن
`borrow(memberId, bookId)`: نسخة واحدة متاحة، حد 3 إعارات نشطة للعضو، غرامة غير مدفوعة تمنع. نفّذها بـ `withTransaction` (client واحد، retry 40001/40P01) ثم اختبر: 50 عضوًا متزامنًا على نسخة واحدة → واحد ينجح؛ عضو واحد 10 طلبات متزامنة بحد 3 → بالضبط 3 (تلميح: هذا write skew — كيف منعته؟ `FOR UPDATE` على صف العضو أم SERIALIZABLE أم قيد؟ وثّق). أرفق جدول: الطريقة، الصحة، الزمن، إعادات المحاولة.

## القسم 3: فحص التصحيح (Debugging Check)

> لكل سيناريو اكتب: المتوقع، الفعلي، الفرضية، التجربة (الأمر/الأداة/الاستعلام)، السبب الجذري، "أين أيضًا قد يوجد هذا؟" — **قبل** فتح الحل.

### 3.1
```
# endpoint يجمع إحصاءات: 40ms في التطوير (500 سجل)، 38s في الإنتاج (200k سجل). CPU 100% نواة واحدة. DB هادئة.
const ids = rows.map(r => r.id); for (const r of rows) r.rank = ids.indexOf(r.id); rows.sort(...)
```
<details><summary>الحل</summary>
الطبقة: Big-O (M3.8). `indexOf` داخل حلقة = O(n²): 500² = 250k (ms) مقابل 200k² = 4×10¹⁰ (دقائق). ×400 بيانات → ×160,000 زمن. التجربة: قس عند 2k/20k (النسبة ≈ 100). الإصلاح: `Map<id, index>` مرة واحدة أو احسب `rank` من الفهرس أثناء المرور. أين أيضًا؟ أي `includes/find/indexOf/some` داخل حلقة؛ `[...acc]` في reduce؛ `shift()`.
</details>

### 3.2
```
# طابور معالجة أحداث في الذاكرة. الذاكرة تنمو 200MB/ساعة في الذروة ثم OOM بعد 6 ساعات. المعالجة نفسها تبطؤ مع الوقت.
while (queue.length) await handle(queue.shift());
```
<details><summary>الحل</summary>
الطبقة: الطوابير (M3.2) + الذاكرة (L2-M2.3). سببان: الطابور غير محدود (المنتج أسرع من المستهلك → نمو خطي → OOM)، و`shift()` O(n) على مصفوفة بملايين → كل عنصر أبطأ → الفجوة تتسع. التجربة: ارسم `queue.length` مع الزمن؛ قس `shift` عند 1M. الإصلاح: head index/ring buffer، **حد** بسياسة صريحة (ارفض 429/أسقط الأقدم/احجب)، مقياس عمق، ثم طابور خارجي. أين أيضًا؟ `pending` arrays، buffers للسجلات، `connections` بلا حد.
</details>

### 3.3
```
# صفحة "طلباتي" تكرّر طلبات بين الصفحات وتفوّت أخرى عند التمرير، فقط عندما يكون المتجر نشطًا.
SELECT * FROM orders WHERE user_id = $1 ORDER BY created_at DESC OFFSET $2 LIMIT 20
```
<details><summary>الحل</summary>
الطبقة: الترقيم (M3.9) + SQL (M3.11). `OFFSET` يتزحزح مع كل إدراج جديد (الصفحة 2 تعيد عنصرًا من الصفحة 1)، و`created_at` بلا tie-break = ترتيب غير حتمي بين الطلبات بنفس الطابع الزمني (دفعات/دقة). التجربة: أدرج أثناء التصفح واحسب التكرارات. الإصلاح: keyset `WHERE (created_at, id) < ($2, $3) ORDER BY created_at DESC, id DESC` + فهرس `(user_id, created_at DESC, id DESC)`. أين أيضًا؟ كل `ORDER BY` بلا مفتاح فريد؛ تقارير تُصدَّر على صفحات.
</details>

### 3.4
```
# بعد إضافة فهرس على users(email) الاستعلام ما زال 2.1s:
EXPLAIN ANALYZE SELECT id FROM users WHERE lower(email) = $1;
→ Seq Scan on users (actual rows=1) Rows Removed by Filter: 4,999,999 Buffers: shared read=61000
```
<details><summary>الحل</summary>
الطبقة: الفهارس (M3.13). دالة على العمود (`lower(email)`) تعطّل فهرس `(email)`؛ الخطة تقولها: Seq Scan + 5M مُسقَطة + 61k صفحة. الإصلاح: فهرس وظيفي `(lower(email))` (أو `citext`)، جزئي `WHERE deleted_at IS NULL` إن وُجد soft delete، `CONCURRENTLY`؛ تحقق: `Index Scan … Buffers: shared hit≈4`. أين أيضًا؟ `date(created_at) = …`، `id::text = …`، `LIKE '%x'`، نوع معامل مختلف.
</details>

### 3.5
```
# حملة تخفيضات: المخزون 25، بيعت 41 قطعة. الكود "يتحقق قبل البيع":
const p = await db.query("SELECT stock FROM products WHERE id=$1"); if (p.stock < 1) return 409;
await db.query("UPDATE products SET stock=$1 WHERE id=$2", [p.stock - 1, id]);
```
<details><summary>الحل</summary>
الطبقة: المعاملات/التزامن (M3.14، L0-M0.7). lost update: قراءة في Node ثم كتابة قيمة؛ 40 طلبًا متزامنًا يقرؤون 25 ويكتبون 24. التجربة: `Promise.all × 50` على مخزون 1. الإصلاح (بالترتيب): `UPDATE … SET stock = stock - 1 WHERE id = $1 AND stock >= 1` وتحقق `rowCount`؛ `CHECK (stock >= 0)` كحكم أخير؛ أو `FOR UPDATE` إن احتجت قرارًا متعدد الخطوات. أين أيضًا؟ العدّادات، الأرصدة، حدود الكوبونات، "اسم مستخدم متاح؟" (→ UNIQUE).
</details>

### 3.6
```
# أحيانًا: ERROR 40P01 deadlock detected — فقط عند طلبين يحويان نفس المنتجين.
for (const line of body.lines) await c.query("UPDATE products SET stock = stock - $2 WHERE id = $1 AND stock >= $2", [line.productId, line.quantity]);
```
<details><summary>الحل</summary>
الطبقة: الأقفال (M3.14، L2-M2.6). الطلب A يقفل (1 ثم 2)، B يقفل (2 ثم 1) بترتيب إدخال العميل → انتظار متبادل → PostgreSQL يقتل أحدهما بعد 1s. الإصلاح: اقفل بترتيب ثابت (`ORDER BY id FOR UPDATE` أولًا أو رتّب البنود بـ `productId`)، وأعد المحاولة على 40P01 كشبكة أمان، `lock_timeout`. أين أيضًا؟ تحويلات بين حسابين، تحديث طرفي علاقة، أي معاملتين تلمسان نفس الصفوف بترتيب مختلف.
</details>

### 3.7
```
# بعد نشر migration: 11 دقيقة من 500 "column total does not exist" ثم تعافٍ تلقائي.
ALTER TABLE orders RENAME COLUMN total TO total_cents;
```
<details><summary>الحل</summary>
الطبقة: migrations (M3.12). النشر المتدرّج: نسخ الكود القديم تعمل على schema الجديد حتى اكتمال النشر (11 دقيقة = مدة النشر). الإصلاح: expand (أضف `total_cents`) → كود يكتب للاثنين ويقرأ الجديد مع fallback → backfill بدفعات → contract (احذف `total`) في نشر لاحق؛ `lock_timeout`؛ فحص CI يرفض `RENAME/DROP` بلا موافقة. أين أيضًا؟ تغيير نوع عمود، إضافة `NOT NULL`، تغيير enum، إعادة تسمية جدول.
</details>

### 3.8
```
# لوحة الإدارة: 50 طلبًا في الصفحة، 9 ثوانٍ. السجل يُظهر 353 استعلامًا لطلب HTTP واحد، كل واحد 3ms.
```
<details><summary>الحل</summary>
الطبقة: N+1 (M3.11) + الكمون (L2-M2.13: الزمن رحلات). 1 + 50 مستخدم + 50 بنود + 150 منتج + 50 مؤسسة ≈ 353؛ 353 × 3ms ≈ 1s لكل مشرف، والـ pool يجف تحت 5 مشرفين. التجربة: عدّاد استعلامات لكل طلب (Server-Timing). الإصلاح: استعلام واحد بـ JOIN + `json_agg` (أو 2–3 بـ `= ANY($ids)`)، قاعدة مراجعة: > 10 استعلامات تحتاج تبريرًا، تنبيه على p99 لعدد الاستعلامات. أين أيضًا؟ ORMs بـ lazy loading، GraphQL resolvers بلا DataLoader، حلقات تستدعي APIs خارجية.
</details>

> أجب بصيغة **Assumption / Constraint / Tradeoff / Risk / Recommendation**. نصف صفحة لكل سؤال. أرقام لا صفات.

### 4.1 — اختيار الهياكل لخدمة واحدة
خدمة إشعارات: 5k حدث/ثانية واردة بثلاثة أصناف SLA، dedup على `event_id` خلال نافذة 10 دقائق، إرسال عبر مزوّد بحد 2k/ثانية، "آخر 1000 خطأ" للتشخيص، وتقرير "أكثر 20 مستلمًا" كل دقيقة. لكل حاجة: الهيكل (M3.1–M3.6)، الحد، السياسة عند الامتلاء، الذاكرة المقدّرة، وما يجب أن يبقى في الذاكرة مقابل ما يذهب إلى DB/Redis.

### 4.2 — ميزانية التعقيد
ضع "ميزانية تعقيد" لمعالجات HTTP في Project 4: الحد الأقصى لعدد الاستعلامات لكل طلب، لحجم النتيجة، لعمق/حجم JSON الوارد، لطول regex ومدخلاته، لزمن أي عمل متزامن (event loop) — مع آلية **فرض** كل حد (middleware، اختبار CI، مقياس + تنبيه) وما يحدث عند تجاوزه (400/413/429/503). برّر كل رقم بحساب.

### 4.3 — تصميم schema من متطلب غامض
المنتج يقول: "نريد تقييمات للمنتجات مع صور وردود البائع، وقائمة أمنيات، وأن يرى المستخدم تاريخ أسعار المنتج". اكتب الأسئلة التي ستطرحها قبل التصميم (≥ 6)، ثم ERD بافتراضاتك، القيود التي تحمي من: تقييمين لنفس الطلب، تقييم بلا شراء، ردّ بائع من مؤسسة أخرى؛ وكيف تخزّن تاريخ الأسعار (جدول فترات vs أحداث) ولماذا، وما الفهارس من الاستعلامات الثلاثة الأهم.

### 4.4 — الفهرسة والنمو
`orders` سيصل 500M صف خلال 3 سنوات، 95% من القراءات على آخر 90 يومًا، التقارير الشهرية على كل التاريخ. صمّم: مجموعة الفهارس (مع تكلفة الكتابة المقدّرة: الجدول يستقبل 2k إدراج/ثانية في الذروة)، هل تحتاج partitioning بالزمن ولماذا/متى، ماذا يحدث لـ keyset pagination وUNIQUE مع التقسيم، وكيف تنشئ فهرسًا جديدًا على 500M صف بلا توقف وكم يستغرق تقريبًا.

### 4.5 — سياسة التزامن للمنتج
وثيقة صفحة واحدة تُفرض على كل الفرق: متى تحديث ذري بشرط، متى `FOR UPDATE` (وبأي ترتيب)، متى SERIALIZABLE + retry، متى قفل تفاؤلي بـ `version`، ما الممنوع داخل المعاملة (I/O خارجي، انتظار مستخدم، > X ms)، timeouts الافتراضية (`lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`)، وكيف يُختبر التزامن قبل الدمج (`Promise.all × N` إلزامي لأي كتابة على مورد مشترك). اربط كل بند بحادثة من هذا المستوى.
